# Prompt: traversal jobs and graphlet services in metagraph-search-service

You are working in `~/git/services/metagraph-search-service`, the FastAPI + FastMCP async service in front of the
MetaGraph `server_query` backends. Read its `CLAUDE.md` first and follow it:
- two separate Redis instances;
- registry changes written to both Supabase and Railway;
- the README tool table generated by `scripts/gen_mcp_tool_table.py`;
- new tests added to the CI list in `.github/workflows/tests.yml`.

**The task.** Extend the service's job scheduling, which today knows only searches, to the new MetaGraph *traversal*
services: label-consistent walks, tries and label-free exploration. Then offer *graphlet services*: tools that let an
agent work with a retrieved traversal locally, without asking the backend again.

**Process.**
1. Work out the design with the owner, who decides it with you.
2. Record it in a design note (`dev-notes/2026-10/traversal-jobs/DESIGN.md`) that answers the open questions at the
   end. Do not implement before the owner approves it.
3. Then implement in increments, each with tests.

In §3, items marked **(required)** are the owner's decisions or follow from the MetaGraph guarantees. Everything
else in §3 is a proposal from the MetaGraph side for you and the owner to weigh, adopt, change or reject.

## 1. What exists on the MetaGraph side

All of this is on branch `gr/labeled-traversal` of `ratschlab/metagraph`, head `d8d3ef86` or later. Read these in
`~/git/services/metagraph/metagraph/docs/`:
- `SPEC-labeled-traversal-core.md`: §5 request, §7 response and guarantees, §7.5 the graphlet format, §10.3 server.
- `DESIGN-traverse-graphlet.md`: the architecture; §3 summary and §3.1 index identity; §5 and §6 the library and
  its tool surface; §14 and §19 the resource contract.
- `source/graphlets.rst`: the library guide, with runnable examples.

**Backend routes** on the same `server_query` processes that serve `/search`:
- `POST /resolve`: which labels carry a sequence's k-mers; used to pick a seed.
- `POST /traverse`: a batch of seeds plus a strategy.
- `GET /traverse/capabilities`: limits, the budgets accepted, `work_check_interval`, `work_bound`, `memory_bound`,
  and the encodings.

Responses are compact JSON. Send `Accept-Encoding: gzip` to get them compressed.

**What a traversal is.** It extends each seed left and right through the annotated de Bruijn graph, following the
labels (samples, genomes, accessions) that carry it. The strategy chooses:
- the label mode:
  - `constrain` with named or derived labels;
  - `annotate`, which is label-free and records the labels it meets, optionally as a beam;
  - `trace`, which is record-exact on coordinate indexes;
- `exhaustive: true`, which returns the complete *trie* up to a radius;
- caps and budgets: `bounds.max_extension_bp`, `time_budget_ms`, `max_memory_mb`, `max_work_units`, and others;
- `output.detail`: `summary`, `tree`, `full` or `graphlet`.

**The graphlet** (`detail: graphlet`) is what agents should use. Per seed it is a small JSON summary (2–4 KB) plus
a body in MGT v1. MGT v1 is a canonical, lossless text format and it is **frozen**; never parse it yourself.

Requests take from milliseconds to minutes.

**Size of one graphlet** (one seed on one index or chunk). These figures were measured on 596 real retrievals: the
real-index test cache, 16 strategies over SRA (primary), UHGG and mini_refseq, at default caps.

| Part | Typical | Range |
|---|---|---|
| Per-seed JSON summary | 2.3 KB | 1–5 KB |
| MGT body | median 7.5 KB | p90 147 KB · p99 3 MB · max 32 MB |
| Body, gzip | about 0.31× the body (median 2.2 KB) | max 2.6 MB |
| Body vs `detail: full` JSON | median 25 % (p90 40 %) | 4.7–11.5 % on large SRA retrievals |
| Parsed Python model (RAM) | 6–17× the body: 145 KB → 2.4 MB, 0.9 MB → 10.8 MB | a 32 MB sequence-heavy body → 40 MB |
| Parse time | about 35 ms per 150 KB, 170 ms per 0.9 MB | 7.6 s for the 32 MB body |

The body size depends mostly on the strategy:

| Strategy | Body median | p90 | max |
|---|---|---|---|
| Label-consistent walks (strict, branch limit 1–2) | 11–15 KB | 50–110 KB | 0.4 MB |
| Tries (exhaustive; label-free exhaustive), capped by live paths | 3–5 KB | 120–180 KB | 0.8 MB |
| Trace (coordinate index) | 30 KB | 85 KB | 0.1 MB |
| Label-free beam, width 1 (long-range exploration) | 44 KB | 360 KB | 0.9 MB |
| Label-free beam, width 20 | 0.8 MB | 3.5 MB | 32 MB |
| Label-free beam, width 20, to 10 kb | 3.6 MB | 3.7 MB | 3.7 MB |

By index, the medians are SRA 4 KB, UHGG 10 KB and mini_refseq 9 KB. The SRA tail is the longest: 297 KB at p90,
32 MB at the maximum.

For a result set, multiply. A fan-out over 100 chunks × 10 seeds gives 1,000 graphlets:
- with label-consistent walks, about 15 MB of bodies (5 MB gzip) plus 2–3 MB of summaries;
- with width-20 beams, 1–3.5 GB of bodies.

The request's caps and budgets bound these numbers: radius, live paths, `max_memory_mb`.

**Guarantees.** Every result carries:
- `outcome {walks, branch_diagnostics, label_evidence, delivery}`;
- `limitations [{kind, knob, limit, observed, effect}]`;
- per arm, `complete_to_bp`;
- `resource_stop` when a budget stopped the walk.

A result with `walks: partial`, or a seed that failed with a stated cause, is a **valid answer**. Never retry it as
an error, and never drop its limitations.

**Index identity.** Each response carries:
- `index_ns`, from the server's `--index-name`;
- `index_fp`, a sha256 manifest from `--index-manifest`, written by `scripts/traversal/index_manifest.py`;
- `index_meta_fp`.

Results from different indexes must never be joined silently. Manifests exist for SRA, UHGG and mini_refseq.

**The Python library** `metagraph.traverse` lives in `metagraph/api/python`. It uses the standard library only and
needs Python ≥ 3.10.
- `parser`/`model`: MGT ↔ model.
- `ops`: local answers — claims, walks, routes, label walks, support changes, splits, sub-tries, compare,
  continuations (`next_request`, `next_requests`).
- `export`: JSON and FASTA.
- `client`: `TraverseClient`.
- `store`: handles, a RAM budget, a disk spool, save/load.
- `mcp_tools`: **19 ready tool functions**:
  - `traverse_capabilities`, `traverse_resolve`, `traverse_fetch`, `traverse_continue`;
  - `graphlet_summary`, `graphlet_claims`, `graphlet_walks`, `graphlet_walk`, `graphlet_labels`,
    `graphlet_support`, `graphlet_splits`, `graphlet_subtrie`, `graphlet_sequence`, `graphlet_compare`,
    `graphlet_export`, `graphlet_save`, `graphlet_load`, `graphlet_list`, `graphlet_free`.

What the tool functions guarantee:
- Each takes JSON-able arguments and returns JSON-able results.
- Each honours `max_bytes`.
- List tools page with MAC-signed cursors.
- Every answer carries an evidence block.
- Errors are results, never exceptions. The codes include `bad_argument`, `bad_arm`, `bad_cursor`,
  `unknown_handle` (with `replayable`), `index_mismatch`, `index_unverifiable`, `release_mismatch`,
  `unverifiable_label_name`, `result_too_large` and `receipt_too_large`.

Tries need no separate code: a trie is a traversal with `exhaustive: true` (or label-free with
`labels.mode: annotate`) and comes back as an ordinary graphlet.

**The architecture decision (the owner's).** Retrieve once from MetaGraph, then process locally in this service.
Follow-up questions about a retrieval never go back to the backend; only a *continuation* (extending from a leaf)
is a new backend job.

## 2. What exists in this service, and what makes a second job type hard

A read-only survey found these (verify each before relying on it).

**Search job lifecycle:**
- `POST /search` is `create_search`, at `app/api/routes_search.py:3483`. It runs rate limits, idempotency,
  overload guards, an access token and a TTL, then enqueues `run_task` (`app/queue/jobs.py`) into per-DB RQ queues
  `db_{id}` and `db_{id}:bulk`.
- Concurrency uses Redis semaphores keyed by **DB id** (a global `META_MAX_CONCURRENCY`, plus per-DB
  `max_conc_searches`).
- Each backend call is retried with tenacity, and each task up to 8 times.
- An in-flight backend call is **never cancelled**: the cancel flag is checked only after the call returns.

Other parts of the service:
- **Backend path.** It is hard-coded to `/search` (`app/metagraph/client.py:162`). The httpx client reads the whole
  response into memory.
- **Results.** One Postgres row per hit; large result sets go to S3 as msgpack partitions.
- **Housekeeping.** The janitor, recovery, admin views, idempotency and the backend cache are all keyed on
  searches and tasks.
- **MCP.** Tools are registered in `app/mcp_server.py` and reach the service through REST loopback, with a 60 s
  timeout and a 240 s long-poll cap. So long jobs must use submit + poll.
- **Handles.** `app/seqhandles.py` keeps sequence handles in Redis with a sliding TTL. They are not scoped to a
  caller.

## 3. Requirements and proposals

### A. Traversal as a second job type

1. **Backends.**
   - Add a registry flag for traversal support, and probe `GET /traverse/capabilities` for each such backend.
     Cache the result and refresh it with the existing fingerprint role.
   - Make the backend path configurable, not `/search` only.
   - Record each backend's index identity: `index_ns`, `index_fp`, `release`.
2. **Jobs fan out like searches (required).** A traversal job runs the same seeds and strategy **in parallel over many
   indexes and index chunks**, exactly as a search fans out over databases and chunks, with one task per (index or
   chunk) × seed batch on the per-DB queues.
   - Its result is a **set of graphlets**: one per (index or chunk, seed). Each comes with a small metadata record:
     - index or chunk, and seed;
     - the index identity;
     - the per-seed JSON summary, outcome and limitations;
     - body size and storage key, and the handle.
   - The agent picks the set up when the job is done and processes it further with the graphlet tools.

   REST endpoints mirror search:
   - submit;
   - status, with progress per index or chunk, and `retry_after_seconds`;
   - result: the list of graphlet records, paged, with handles. Bodies are fetched through the handles or presigned
     links, never inlined in the list;
   - stop.

   Reuse the access-token, TTL, idempotency (request fingerprint plus index identity), rate-limit and overload
   machinery.
3. **Scheduling.**
   - Traversal shares backends with search. It can be heavy (minutes, GBs), and staging and production share
     backends.
   - Design the caps so that traversal cannot starve search latency: e.g. a separate traversal semaphore per
     backend *host*, counted against a global cap.
   - Bulk or exhaustive requests go to a lower-priority queue.
4. **Budgets as policy.**
   - The service sets `bounds` from caller tier and backend capabilities: `time_budget_ms` at most the backend's
     limit, plus `max_memory_mb` and `max_work_units`.
   - It never sends an unbounded request.
   - It always requests `detail: graphlet` for agent use; `full` only for explicit exports.
5. **Retries (required in substance).** Retry transport failures and 5xx only. A 4xx is a caller error. A 200 with partial or failed seeds is
   a result. Never re-run an expensive exhaustive request automatically after it returned.
6. **Storage: metadata in Postgres and Redis, graphlets outside the database (required).** Graphlets are never
   displayed on the website, so **they are not stored in Postgres**. They must still be stored somewhere an agent
   can pick them up and keep working with them later. Where and how are design questions: the bullets below are
   proposals.
   - **Postgres and Redis hold job metadata only.** That means the job and task rows, status and progress, and per
     graphlet:
     - index or chunk, seed, identity;
     - the small summary, outcome and limitation kinds;
     - size, storage key and expiry.

     Keep it in its own tables (e.g. `traversal_jobs`, `traversal_tasks`, `graphlet_refs`); do not overload
     `searches`/`results`.
   - **The bodies** (the per-seed MGT text plus its JSON summary, gzip-compressed) go to an object store: S3 where
     it is enabled, otherwise a file store on a volume the API and workers share. They are keyed by sha256 so that
     identical bodies are stored once. They must stay retrievable until the job expires, so an agent can pick them
     up later, across sessions and workers.
   - The janitor deletes the bodies with the job: the same TTL as searches, extended while handles are in use.
   - Workers stream a backend response straight to the store; they never hold a multi-MB body in a DB row.
7. **Cancellation.** Queued jobs are cancelled. In-flight backend requests run to their `time_budget_ms`, and the
   result must say so.
8. **Observability.** Metrics (jobs, durations, body bytes, partial/failed seeds, `resource_stop` kinds, work units
   used), admin views and audit entries, following the existing patterns.

### B. Graphlet services (local processing)

**Open design question: does the agent download the graphlets, or manipulate them inside the service?** The
answer probably depends on the size of the graphlets and the number of results (measured sizes in §1), and on
whether the agent can run code. The options and their trade-offs:
- **In the service.** The agent works through the graphlet tools while the bodies stay in the service. This fits
  when:
  - the agent has no code execution or filesystem, which is true of most MCP clients;
  - the set is large, because the agent only ever sees small views;
  - the service should keep enforcing the evidence and limitation rules on every answer.
- **Download (export).** A code-capable agent (Claude Code, notebooks) fetches selected graphlets and processes them
  with the same library, `pip install` from `metagraph/api/python`, on its own side. This fits when:
  - the selection is small enough to fetch;
  - the agent wants analysis the tools do not offer;
  - the service should not spend CPU or RAM on it.

  A possible form: a bundle of the selected graphlets (MGT bodies, summaries, a manifest with identity and
  limitations) behind one presigned link, plus single-graphlet links.
- **Both**, with the result set guiding the choice.
- **The sizes that decide** (the measured figures are in §1).
  - Summaries are about 2 KB each.
  - Bodies are mostly tens of KB, with a long tail to tens of MB for wide label-free beams.
  - A parsed model takes 6–17× its body in RAM on whichever side parses it.
  - A fan-out over a chunked index (SRA has many chunks) times many seeds can reach thousands of graphlets, from
    tens of MB to GBs.
  - One proposal: every result record states its body size, the result set states totals, and the job's receipt
    suggests a mode, for example: "N graphlets, X MB: overview and drill-down in the service; download the K
    graphlets you select".
  - In either mode, an overview of a large set can come from the stored metadata, without loading bodies.
- **If graphlets are processed in the service, it must bound that computation (required in that case).** The
  library's local operations (compare, routes, export) have no
  work or allocation budget yet: design stage L, not enforced, and `max_bytes` bounds only the bytes returned. Run
  them in worker processes with per-call time and memory limits, and charge them to the caller's quota, so one
  agent's `compare` on two multi-MB graphlets cannot starve the others.

1. **Register the tools.** Expose the library's tool functions as MCP tools; REST equivalents are optional.
   - `traverse_fetch` and `traverse_continue` become *submit + poll* on the job system. When the job finishes, they
     return a handle and the summary.
   - The `graphlet_*` tools answer locally.
   - Keep the library's evidence blocks, limitations, cursors, `max_bytes` behaviour and error codes. Map the errors
     onto the service's `_err` convention without losing their codes.
2. **Handles in a multi-process deployment.** The library's `store` lives inside one process. Design the shared
   version:
   - A handle is an opaque bearer id in Redis, like seqhandles, mapping to (job id, index or chunk, seed, body
     hash, identity) with a TTL.
   - A finished job hands out one handle per graphlet in its result set, plus a job-level handle for the set.
   - Bodies live in the object or file store above.
   - Each worker keeps an LRU of parsed models under a RAM budget and rebuilds on a miss. Parsing takes from 46 ms
     to about 1 s for large bodies, and a parsed model is roughly 10× the body size.
   - The cursor MAC secret is shared across workers, from settings.
   - `graphlet_save`/`graphlet_load`/`graphlet_export` map to service storage and presigned links, not local
     files.
   - Decide whether handles are scoped to the caller (API key or access token); seqhandles are not.
3. **Strategy presets.** Agents should not hand-craft strategies. Offer named presets with defaults and limits taken
   from capabilities:
   - `walk`: label-consistent walks;
   - `trie`: exhaustive constrain trie to a radius;
   - `label_free_trie`: annotate exhaustive;
   - `beam`: label-free, width 1, most-supported, for long-range exploration;
   - `trace`: coordinate indexes only.

   Expose the full strategy only as an advanced option.
4. **Working across the result set.**
   - Set-level tools over a job's graphlets: a per-index or per-chunk overview from the stored metadata alone (no
     body loaded): which indexes reached how far, outcomes, limitations, top labels.
   - Load bodies lazily for drill-down.
   - The library's `compare` refuses graphlets from different indexes (identity), and that stays. Cross-index views
     are summaries over the set, never silent joins of graphlets.
5. **Joins with search (nice to have).** Start a traversal from a search hit: the query, or a window of it, as the
   seed, and the hit's labels as the seed labels.
6. **Quotas.** Charge traversal and continuation jobs against caller quotas. Use the `work_units` and
   `resource_stop` values the responses report.

## 4. Constraints

- **The library.** Do not modify the metagraph repository. Consume `metagraph.traverse` as a pinned dependency: a git
  URL with subdirectory `metagraph/api/python` at a commit, or a vendored copy with a version check. Report any
  backend change you need as a separate request.
- **No search changes.** Search behaviour and performance must not change. Run the existing suites.
- **Privacy.** Traversal requests contain sequences; the search privacy rules apply.
- **Formats.** MGT v1 is frozen and may only be read through the library.

## 5. Tests and acceptance

- **Unit and API tests** with a fake backend that replays the committed fixtures. These are in the metagraph repo:
  - `metagraph/api/python/tests/data/traverse/documents/`, CLI-generated requests and responses, including
    `budgets/`;
  - `.../traverse/real/`, 16 real SRA, UHGG and mini_refseq retrievals.
- **One integration test** against a real `server_query` built from the branch, on the mini_refseq index:
  `scripts/traversal/build_mini_refseq.sh` builds it in minutes. Cover:
  - submit;
  - poll;
  - handle;
  - local queries;
  - a continuation;
  - an `index_mismatch` after the backend's manifest changes.

**Acceptance:**
- An agent can:
  - go from `catalog` to `traverse_fetch` with a preset over several indexes and chunks;
  - poll to a result set of graphlet handles;
  - get the cross-index overview;
  - drill into one graphlet: list walks, get a FASTA export, compare two retrievals of the same index, and continue
    from a leaf.

  It never parses MGT, and it sees every limitation.
- No graphlet body is stored in Postgres.
- Bodies stay retrievable by handle across workers and sessions until the job expires.
- Partial results are delivered and stated, not retried.
- Search latency under concurrent traversal load stays within the existing SLOs.

## 6. Open questions the design must answer

0. Do agents download graphlets, manipulate them inside the service, or both? From which graphlet sizes and result
   counts does each fit, and how is the choice offered to the agent?
1. Share the per-DB semaphores with search, or use separate per-host traversal caps? With what defaults?
2. Which object or file store holds the bodies when S3 is off? How long do they live, and how does the TTL
   interact with handles still in use? Is deduplication by sha256 safe across callers?
3. Handle scope (caller, session, public bearer) and TTL? What happens to a handle when its traversal expires?
4. Is `/resolve` synchronous (it is fast) or a job? Is `traverse_fetch` ever inline for small requests?
5. Budget defaults per caller tier, and how they are surfaced to agents.
6. How continuation jobs link to their parents (lineage and identity checks), and how presets carry over.
7. How traversal usage counts against quotas and rate limits.
8. If both modes are offered: the thresholds, the download format, and the per-call limits for in-service
   operations.
9. Task granularity for the fan-out: one task per (index or chunk, seed batch)? How are many seeds batched per
   backend request (the backend accepts a batch)? How do partial failures of some indexes or chunks show up in the
   job status and the result set?
